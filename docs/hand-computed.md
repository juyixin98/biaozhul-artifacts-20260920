# 手算样例（验收依据）

本文档逐行推演若干短序列，作为“手算对照”的验收依据；同样的预期已固化在
`tests/HandComputedTest.java` 中，可自动复算。

统一约定（除特别说明外）：

- 窗口 `W = 100ms`，匹配条件 `0 ≤ tB − tA ≤ 100`（**两端闭区间**）
- 模式策略 `ALL_CANDIDATES`（所有合格的 (A,B) 对都输出；A 匹配后仍可再匹配）
- 事件时间模式，允许迟到 `L = 0`，watermark = 已见最大事件时间
- key 相同（多 key 例子除外）
- 迟到判定：`timestamp < watermark` 才算迟到；`timestamp == watermark` 不算

全序规则：事件按 `(timestamp, seq)` 排序，`seq` 为到达序号。时间戳相同的事件，
先到达的排在前面。

---

## 例 1：基本匹配 A → B

输入（按到达顺序）：

| seq | id | 类型 | t  |
|----:|----|------|---:|
| 0 | A1 | A | 0 |
| 1 | B2 | B | 50 |

逐步推演：

1. `A1@0`：等待集合 `{A1(deadline=100)}`。watermark=0。
2. `B2@50`：watermark→50；没有 A 超时（50 > 100 不成立）。
   对 A1：`0 ≤ 50−0 ≤ 100` 成立，且开区间 (A1,B2) 内无 C。
   → 输出匹配 **(A1, B2)**。

结果：`matches = [k|A1|B2]`，无移除、无迟到。

---

## 例 2：多个 A 候选（重叠匹配）

| seq | id | 类型 | t  |
|----:|----|------|---:|
| 0 | A1 | A | 0 |
| 1 | A2 | A | 10 |
| 2 | B3 | B | 60 |

1. A1 等待；A2 等待：`{A1, A2}`。
2. B3@60 与每个等待中的 A 比较：
   - A1：60−0 = 60 ∈ [0,100]，区间无 C → 匹配；
   - A2：60−10 = 50 ∈ [0,100]，区间无 C → 匹配。
3. 输出顺序按 A 的全序：**(A1,B3)、(A2,B3)**。两个 A 都保留。

扩展：再来 `B4@80`（例 2b），A1、A2 仍在窗内，各再匹配一次，共 4 个匹配：

```
(A1,B3) (A2,B3) (A1,B4) (A2,B4)
```

这就是 `ALL_CANDIDATES` 的重叠语义：既允许“一对多”（一个 B 对多 A），
也允许“多对一”（一个 A 对多 B）。

---

## 例 3：C 打断

| seq | id | 类型 | t  |
|----:|----|------|---:|
| 0 | A1 | A | 0 |
| 1 | C2 | C | 40 |
| 2 | B3 | B | 60 |

1. A1 等待。
2. C2@40：watermark→40（A1 deadline=100 未超时）。C 在全序上位于 A1 之后，
   A1 被打断移除，记录 `INTERRUPTED_BY_C`，打断者 `cId=C2`。
3. B3@60：等待集合为空 → 无匹配。

结果：无匹配；`removed = [A1 INTERRUPTED_BY_C by C2]`。

**关键点：C 只打断“在全序上位于它之前”的等待 A。** 若 C 到达时某个 A 已经超时，
则该 A 记 `TIMEOUT` 而不是被 C 打断（见例 4 的边界讨论）。

例 3b：`A1@0, A2@30, C3@50, B4@90` —— C3 在两个 A 之后，A1、A2 都被打断；
B4 无匹配；两次 `INTERRUPTED_BY_C`。

---

## 例 4：超时

| seq | id | 类型 | t  |
|----:|----|------|---:|
| 0 | A1 | A | 0 |
| 1 | B2 | B | 120 |

1. A1@0 等待，deadline = 0+100 = 100。
2. B2@120：watermark→120。**watermark=120 > deadline=100**，A1 先被超时清理
   （原因 `TIMEOUT`），随后 B2 在空等待集合上不匹配。

结果：无匹配；`removed = [A1 TIMEOUT]`。

> 超时判定是严格不等式 `watermark > tA + W`。
> 这保证了 B 恰好在 `tA+W` 到达时仍能匹配（闭区间右端），而到了 `tA+W+1`
> （watermark 严格越过窗口上界）才超时。

例 4b：`A1@0, B2@40` 先匹配成功；之后手动把 watermark 推到 101，A1 退场，
原因为 `EXPIRED_AFTER_MATCH`（匹配成功过、窗口结束后清理；仅统计用）。

---

## 例 5：同一时间戳的事件次序

全序 `(timestamp, seq)` 唯一确定先后。三个事件同为 `t=100`：

**例 5：到达序 A, C, B（同刻）**

| seq | id | 类型 | t  |
|----:|----|------|---:|
| 0 | A1 | A | 100 |
| 1 | C2 | C | 100 |
| 2 | B3 | B | 100 |

- A1 等待；C2 与 A1 同刻但 seq 更大（在 A1 之后）→ A1 被 `INTERRUPTED_BY_C`；
- B3 到达时等待集合为空 → 无匹配。

**例 5b：到达序 A, B（同刻）**：seq A < seq B 且 tA==tB，窗口差 0 ∈ [0,100]
且无 C → **匹配 (A1,B2)**。即“同刻但 A 先到”合法。

**例 5c：到达序 B, A（同刻）**：B 到达时还没有等待中的 A；A 随后进入等待，
不会回溯匹配更早的 B → 无匹配。

---

## 例 6：窗口边界

- `A@0, B@100`：100−0 = 100 ≤ W → **匹配**（右端闭合）。
- `A@0, B@101`：101 > 100；watermark=101 > deadline=100 → A 先超时，**不匹配**。

---

## 例 7：乱序与迟到（L=0，DROP）

到达顺序：

| 到达序 | id | 类型 | t  |
|-------:|----|------|---:|
| 1 | A1 | A | 0 |
| 2 | B2 | B | 50 |
| 3 | A3 | A | 10 |  ← 迟到
| 4 | B4 | B | 60 |

1. A1@0 等待；B2@50 与 A1 匹配，watermark=50。
2. A3@10 到达：`10 < watermark(50)` → **迟到**。策略 DROP：A3 被静默丢弃，
   记 `lateDropped=[A3]`，不改变任何状态、不推进 watermark。
3. B4@60：等待集合里只有 A1 → 只匹配 **(A1,B4)**。被丢弃的 A3 不参与。

在线结果：`matches = [(A1,B2), (A1,B4)]`。

---

## 例 8：重放（无迟到假设下的理想结果）

对例 7 的**同一事件集合**做确定性重放：先按 `(timestamp, 到达序)` 排序，
再喂给一个全新引擎 / 交给暴力参考实现。排序后：

```
A1@0, A3@10, B2@50, B4@60
```

此时不存在迟到：

- B2@50 同时匹配 A1（50）、A3（40）；
- B4@60 同时匹配 A1（60）、A2 即 A3（50）；

理想结果共 4 个匹配：

```
(A1,B2) (A3,B2) (A1,B4) (A3,B4)
```

`POST /replay` 会同时给出“流式重放结果”和“暴力参考结果”，并标注
`consistent: true`。这体现了“在线受 watermark 限制 vs 离线重放补算”的差异——
两者都是确定性的，服务如实返回，不做静默修正。

---

## 例 9：REJECT 策略（迟到 → 整批原子拒绝）

配置 `latePolicy=REJECT`：

1. `A1@0, B2@80` → 匹配，watermark=80。
2. 提交批次 `[A3@5, A4@90]`：A3 的 5 < 80 迟到。
   - 引擎在**改动任何状态之前**完成整批判定，发现迟到事件 → 抛错（HTTP 422），
     A4 也不会进入状态。
3. 再来 `B5@95`：只可能匹配 A1 → 输出 **(A1,B5)**，证明回滚干净。

---

## 例 10：多 key 互相隔离

| id | key | 类型 | t  |
|----|-----|------|---:|
| A1 | k1 | A | 0 |
| C2 | k2 | C | 10 |
| B3 | k1 | B | 20 |

k2 的 C 不影响 k1 的 A1 → 输出 **(k1: A1, B3)**。等待状态、watermark（事件时间）
都按 key 独立维护。

## 附：处理时间模式的手算

处理时间模式忽略事件自带 timestamp，改用“到达时刻的注入时钟读数”。窗口超时由
注入调度器在 `tA + W + 1` 触发（同样保证 `[tA, tA+W]` 闭区间）：

- t=0 到 A，t=50 到 B → 匹配（即使两个事件 JSON 里的 timestamp 都是别的值）。
- t=0 到 A，把时钟/调度器推进到 101 → A 超时；t=101 的 B 不匹配。
- 同一时钟读数的一批事件，按批内顺序定全序：`[A,B]` 匹配，`[B,A]` 不匹配。

由于时钟和调度器都可注入，处理时间的这些场景在 `ProcessingTimeTest` 中同样是
确定性自动测试（`ManualClock` + `ManualScheduler`）。
