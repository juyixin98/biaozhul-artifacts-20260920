# 设计说明

## 1. 问题与关键不变量

需求中的"动态规则版本绑定"本质是一个**事件时间（event-time）维度的版本路由**
问题，难点不在过滤本身，而在以下四条不变量：

1. **版本不可变**：已发布规则永不被就地修改；任何变更都是"新版本 + 新绑定"。
2. **按事件时间路由**：事件用哪一版规则只取决于它自己的 `eventTime`，与到达
   顺序无关——这是乱序/晚到事件能得到正确历史结果的根本原因。
3. **不静默降级**：事件时间没有任何版本覆盖（早于首边界），或对应版本已被
   回收时，必须显式拒绝，禁止回退到"最新规则"。否则数据会被悄悄错误过滤，
   且难以察觉。
4. **回收有前提**：只要某个历史版本"理论上还可能被需要"，就不能回收它。

## 2. 时间模型：两种时间严格分离

| 时间 | 来源 | 用途 |
| --- | --- | --- |
| 事件时间 `eventTime` | 事件自带，不可信、可乱序 | 选择规则版本；推进水位线；判定晚到 |
| 处理时间 `processingTime` | 注入的 `Clock`（到达时刻） | 记录到达、周期调度、发布/回收审计时间 |

领域代码中没有任何一处直接调用 `System.currentTimeMillis()`；全部经由
`Clock`。`manual` 模式用 `ManualClock`（时间不动，只有显式推进才变），
`ManualScheduler.runDue()` 按经过的完整周期数**补跑**（catch-up 语义），
因此"把时钟拨过 N 个周期再 tick，任务恰好跑 N 次"，测试确定性、无睡眠。

## 3. 区间绑定与版本解析

`RuleVersionTable` 内部用 `TreeMap<effectiveFrom, Binding>` 维护绑定。
解析版本即一次 `floorEntry(eventTime)`：

```
floor 结果为空           -> MISSING_RULE_VERSION（拒绝）
命中绑定指向墓碑         -> RECLAIMED_RULE_VERSION（拒绝）
否则                     -> 返回该不可变版本与命中绑定
```

左闭右开语义由 floor 自然得到：`t=1000` 落在 `from=1000` 的绑定上。
新绑定要求 `effectiveFrom > 当前最大边界`，所以历史区间一旦形成即冻结；
回滚也是写入一条新的 floor 记录，而不是改写旧记录。

选择 floor + TreeMap 而非区间数组，是因为它让"边界时刻归属下一版本"
这一最易错的语义变成数据结构的自然行为，无需手写二分与差一判断。

## 4. 水位线与晚到事件

```
watermark = max(eventTime of 已成功解析版本的事件) − allowedLateness
```

两个刻意的顺序决定：

- **先解析版本、再推进水位线**。版本缺失/已回收是拒绝，这类事件不应推进
  水位线，否则一条无效事件会错误地宣布"更早的事件都晚到了"。
- **晚到事件不丢弃**。`eventTime < watermark` 只打 `late` 标记，随后照常
  用 floor 出的历史版本求值。这正是"迟到事件使用对应历史版本"。

水位线只进不退，晚到事件不改变它（`max` 天然保证）。

## 5. 历史版本回收前提

设 v 的所有生效区间为 `[f_i, t_i)`（最后一条绑定的 t 为 +∞）。回收前提：

```
(所有 t_i 均有限)                         —— 条件 1：v 不是当前版本
且 max(t_i) ≤ watermark − retentionHorizon —— 条件 2：晚到事件已无可能需要 v
```

- 条件 1 排除"当前版本"（它持有向右无限的区间），也正确处理**回滚后一个版本
  拥有多段区间**的情况：只要其中一段未闭合，就不可回收。
- 条件 2 中 `retentionHorizon` 是允许乱序窗口之外的**额外**保留时长，是运维
  可调的保守余量；取 0 时闸门恰为水位线，`max(t_i) ≤ WM` 即可回收。
- 边界用 `≤`：在闸门时刻恰好到期属于可回收，语义可被精确定点测试。

回收是**逻辑删除（墓碑）**而非物理抹除：

- 删除规则体（谓词不可再用，释放内存，达到回收目的）；
- 绑定记录保留（审计：能回答"某事件时间本该用哪版规则"）；
- floor 解析到墓碑时返回 `RECLAIMED_RULE_VERSION`，而不是改判当前规则。

自动回收是同一前提判断的批量应用（`reclaimEligible`），可挂到注入的
`Scheduler` 上周期执行；manual 模式下随 `/admin/tick` 确定性触发。

## 6. 参考实现的定位

`EventProcessor` 对每条事件做一次版本解析 + 一次谓词求值，并完整保留每条
`ProcessResult`（事件时间、处理时间、前后水位线、late、命中版本、绑定序号、
拒绝原因）。这是**小数据精确参考实现**：不做近似、不做聚合丢弃，输出可逐条
人工核对，也可作为未来流式/大规模实现的对照基线。谓词求值器
（`Predicates`）同样是直接的树递归，无外部表达式引擎。

## 7. 并发与失败处理

- `RuleVersionTable` 以版本表为锁，保证"发布/回滚/回收/解析/快照"的原子性；
  `EventProcessor` 的结果列表独立加锁。HTTP 层使用固定线程池，状态变更
  串行化在表锁上。
- 请求分层错误：JSON/入参/规则规约错误 → 400；语义冲突（边界、版本状态、
  回收前提）→ 409，均带稳定错误码。业务拒绝是 200 内的逐事件状态，避免把
  "这条事件无法判定"与"请求本身错误"混为一谈，也让批量接口能部分成功。
- 周期任务内部异常被捕获记录，不会杀死后续调度（与
  `ScheduledExecutorService.scheduleAtFixedRate` 的默认行为相反）。

## 8. 明确的范围边界（非目标）

- 不做持久化：进程内状态，重启为空（无外部系统是需求约束）。
- 不接入消息队列/Kafka：事件经 HTTP 同步提交。
- 不做规则表达式的图灵完备脚本：仅提供声明式谓词算子，安全且可静态校验。
- 不做前端。
- 不做高吞吐优化：以"精确、可读、可核对"为首要目标。
