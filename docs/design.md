# 设计说明与正确性

## 1. 分层模型与“一次请求原子扣减两层”

系统有一个**全局桶**和若干**租户桶**。一次请求（`tokens=n`）只有当
全局层与该租户层在**同一临界区**内都判定可付时，才同时扣减；否则两层都
不修改。

锁顺序全局统一为：

```
Limiter.mu (租户表)  →  global.mu  →  tenant.mu
```

- `acquire(tenant, now)` 一次取齐三层锁（必要时惰性创建租户桶）。
- 判定路径里的 `settle()` 是**纯时间投影**：只把“自锚点以来应补充的令牌”
  物化，从不消费。因此“先看后不扣”不会改变任何存量。
- 拒绝分支在释放全部锁之后才发事件，避免事件接收器（sink）反过来影响锁。

由此直接得到**无部分消费**：两层扣减语句都发生在所有锁持有期间，中间不存在
释放点，任何并发请求看到的状态要么是“都没扣”，要么是“都已扣”。

并发正确性由 `-race` 与随机属性测试守护：
`TestTwoLayerStockConservation` 在停止补充（存量守恒最容易校验）下并发请求，
断言每个桶都满足 `remaining + consumed == initial`，且所有租户的消费量之和
恒等于全局层的授权量（两层不会对不上账）。

## 2. 整数令牌桶，无浮点

令牌与容量都是 `int64`。亚令牌进度用“分子刻度”余数表示：

```
gained = (rem + num * elapsed) / den      // floor
rem    = (rem + num * elapsed) mod den
```

- `rem ∈ [0, den)`，表示“已累积但还不够一整个令牌”的那段进度。
- `num * elapsed` 用 128 位无符号乘法（`math/bits.Mul64`）保存，
  除以 `den` 用手写 128/64 长除法（`bits.Div64`）。
- 在取值边界内（`num ≤ 1e9`，`elapsed` 为纳秒），乘积远小于 2^100，安全。
- 无论把一段时间切成多少个小步分别 `settle`，结果都与一次性计算一致——
  这由取整余数的自然携带保证，测试用数千次 1ms 小步精确验证
  （如 1 token/10s 的场景不会出现 `0.1*100=9.9999...` 这类浮点漂移）。

“需要等待多久”用向上取整：

```
t = ceil((missing*den - rem) / num)
```

`math.go` 另有针对 `math/big` 的随机预言机测试（20000 组随机 128 位被除数），
确保自写除法与大整数库逐位一致。

## 3. 单调时钟

- 时间统一为 `clock.Instant`（单调纳秒），补充只看相邻操作的纳秒差，
  不接触墙上时钟，不受系统时间回拨/跳变影响。
- `RealClock` 用于生产；`FakeClock` 用 `Advance(d)` 手动驱动，
  到点的定时器按 `(时刻, 插入顺序)` 在同一临界区内取出执行，
  因此测试能对“就绪时刻”“提前一毫秒不得执行”做精确断言。
- 若观测到 `now < 锚点`，桶直接当作时间未前进处理，绝不“倒着造令牌”。

## 4. 未来预留（firm reservation）与调度器

普通立即请求不能借用未来令牌；而 `/schedule` 需要“将来某刻执行”。实现采用
Guava `SmoothBursty` 风格的“下一张可用令牌时刻”记账：

- 桶的锚点 `last` 允许落在**未来**：表示之前的预留已经把“到那个时刻才会
  补充出来的令牌”提前锁定。
- `readyLocked(tokens, now)` 返回在当前承诺下最早可服务时刻：
  若锚点已在未来，则新预留排在它后面（`eff = max(now, last)`）。
- `Reserve` 在一次持锁内分别求全局、租户的就绪时刻，取较大者 `ready`，
  再让两层在同一个 `ready` 上 `reserveLocked`（结算到 `ready` 并扣减、
  锚点推进到 `ready`）。因为“算就绪”和“提交”之间锁不释放，
  天然不存在读-判-提交窗口，也就**不需要乐观重试**，更不可能两层只提交一层。
- 预留成功后由可替换的 `clock.Scheduler` 在 `ready` 触发执行器回调。
- 预留是**坚定（firm）**的：令牌在预留时即出账；取消不退款。这保证了
  “已承诺工作量 ≤ 实际供给”，多个并发提交不会超额承诺。
  立即 `/request` 看不到这些未来令牌（`committed=true` 时存量是“在锚点
  才兑现”的承诺值），避免一女二嫁。

## 5. 动态速率 / 容量，绝不凭空增发

`applyConfigLocked` 在改配置前先按旧速率结算到当前时刻，然后：

1. **容量缩小**：超过新容量的存量被钳制（销毁）。
2. **容量扩大**：仅抬高上限，存量不变（不发令牌）。
3. **速率改变**：把与速率无关的分数 `rem/den`（“欠的那部分令牌”）保守换算到
   新周期 `rem_new = floor(rem * den_new / den)`。向下取整意味着可能损失
   极小的一段进度，但绝不会无中生有。
4. **停止→恢复（num 0→正）**：丢弃余数并把锚点重置为当前时刻，
   停止的那段时间不参与补涨。
5. **运行中→停止（正→0）**：冻结，现有整令牌仍可消费，之后永不补充。

每次切换都发 `config_changed` 事件，携带 `before`/`after` 快照，便于审计。

## 6. 结构化事件

- `event.Bus` 给每个事件打全局单调 `seq` 与单调时间戳 `at_ns`，扇出到多个 sink。
- 内置 `MemorySink`（供 `/events` 读取）与 `JSONSink`（JSON Lines 落盘）。
- 一次两层操作产生**成对**事件（global/tenant 各一条），字段里带
  `remaining`/`wait_ns`/`reason`，因此“拒绝是否发生部分消费”可以直接从
  事件流审计，而不必猜测。

## 7. 可替换性

| 角色            | 接口                          | 生产实现      | 测试实现     |
|-----------------|-------------------------------|---------------|--------------|
| 时钟            | `clock.Clock`                 | `RealClock`   | `FakeClock`  |
| 延迟执行器      | `clock.Scheduler`             | `RealClock`   | `FakeClock`  |
| 事件接收        | `event.Sink`                  | JSONL/内存    | 内存/自定义  |

库本身不创建 goroutine 来“补充令牌”——补充是惰性投影；只有执行器在
作业就绪时触发一次回调。

## 8. 边界与已知取舍

- 令牌量为整数；不支持小数令牌的即时消费（用更长的 `rate_den_ns` 表达慢速率）。
- 预留为坚定语义，不提供取消退款（可在上层另建“释放补偿”策略）。
- 状态保存在内存，进程重启不持久化；事件可用 `-events` 落盘做审计回放。
- 单机实现；多实例共享预算需要外置存储，不在本项目范围。
