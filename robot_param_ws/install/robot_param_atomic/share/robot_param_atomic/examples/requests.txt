# Example client requests
#
# Every update is an atomic compare-and-swap batch: it carries the version the
# caller believes is current (expected_version) plus the WHOLE desired
# snapshot. The server applies it only if the version still matches and the
# resulting snapshot satisfies the cross-field invariant
# (cache_length_s >= 2 * allowed_latency_s).
#
# These files are consumed by scripts/acceptance.sh and can also be read by
# humans. Field order:
#   expected_version sampling_rate_hz cache_length_s allowed_latency_s
# A value of -1 means "leave this field unchanged" (partial update).

# 1) Boot snapshot. Valid: cache 1.0 >= 2 * 0.25 = 0.5.
0  100   1.0  0.25

# 2) Commit against a fresh store -> version 1. Valid: 2.0 >= 2*0.5 = 1.0.
0  200   2.0  0.5

# 3) HEADLINE NEGATIVE CASE.
#    Each field is legal on its own (rate>0, cache>=0, latency>=0), but the
#    COMBINATION is illegal: 0.4 < 2*0.3 = 0.6. The whole batch is rejected and
#    nothing changes. Send with expected_version = current version.
1  1000  0.4  0.3

# 4) Stale token: after version 1 was committed, an old client still uses 0.
#    Rejected with REJECT_STALE_VERSION (code 2).
0  300   4.0  1.0

# 5) Correct token -> version 2. Valid: 4.0 >= 2*1.0.
1  300   4.0  1.0

# 6) Partial patch (fields left unchanged are -1). Raise latency to 1.9;
#    cache stays 4.0 and 4.0 >= 2*1.9 = 3.8, so it commits -> version 3.
2  -1    -1   1.9

# 7) Partial patch that BREAKS the invariant: latency 3.1 needs cache >= 6.2
#    but cache is left at 6.0 -> rejected code 1, state stays at caller's
#    expected version.
3  -1    -1   3.1
