# bse — streaming binary codec with schema evolution

`bse` is a pure-backend Rust library plus a small command-line **JSON control
entry point** for a documented binary message format called **BSE1**.

It demonstrates schema evolution for a field-numbered binary format:

* field numbers identify fields (positions are irrelevant);
* `required` / `optional` / `repeated` cardinalities, with packed repeated
  scalars;
* **unknown fields are captured verbatim and forwarded** through services that
  use an older schema — including unknown fields nested inside sub-messages;
* **incompatible type changes are rejected** rather than misread;
* an absent field is always distinguishable from an explicit zero / empty
  string / `false`;
* decoding is **streaming** and bounded: per-value length, total output size
  and nesting depth are all capped.

The core algorithms are implemented from scratch with **no third-party
dependencies**: LEB128 varints, zig-zag, the JSON parser/serializer and base64
are all in `src/`.

The normative byte-level specification lives in **[FORMAT.md](FORMAT.md)**.

## Project layout

```
Cargo.toml
src/
  error.rs    typed error enum
  wire.rs     BSE1 wire format: varint/zig-zag, streaming Reader/Writer, envelope, limits
  schema.rs   schema model + evolution compatibility matrix
  value.rs    dynamic Message/Value/Field (with an explicit Missing state)
  codec.rs    schema-driven streaming encoder/decoder, unknown-field capture
  json.rs     dependency-free JSON parser/serializer + base64
  jsonio.rs   JSON <-> schema/message conversion, hex helpers
  api.rs      JSON control entry point (encode/decode/forward/compat/truncate)
  lib.rs      crate root
  main.rs     CLI
examples/     schema + request samples and a generator/demo script
tests/        integration tests (evolution, limits, packed/scalars, JSON API)
FORMAT.md     normative wire-format specification
```

## The JSON control entry point

Everything is one JSON request in, one JSON response out. The CLI reads a
request from a file or stdin and writes the response to stdout:

```bash
bse --pretty -f examples/req_encode_v1.json     # from a file
cat request.json | bse --pretty                 # from stdin
```

On success the response is `{"ok": true, "result": {...}}`; on failure it is
`{"ok": false, "error": "..."}` and the process exits non-zero.

### Operations

| `op`       | Request keys                                              | Result |
|------------|-----------------------------------------------------------|--------|
| `encode`   | `schema`, `message`, optional `max_output`               | `data_b64`, `data_hex`, byte counts |
| `decode`   | `schema`, `data_b64`/`data_hex`, optional limits         | `message` (with presence wrappers), `stats` |
| `forward`  | `schema`, data, optional `set` patch, limits             | re-encoded bytes that preserve unknown fields |
| `compat`   | `old_schema`, `new_schema`                               | per-field compatibility report |
| `truncate` | `data_b64`/`data_hex`, `keep`                            | envelope payload cut to `keep` bytes (for truncation tests) |

Optional decode limits: `max_value_len`, `max_output`, `max_depth`.

### Presence in the message JSON

Input shorthand: omitted key or `null` means **absent**; any present value is
explicit, so `{"id": 0}` is an explicit zero. Explicit wrappers are also
accepted on input and are always used on output:

```json
{ "id": {"present": 0}, "email": {"missing": true}, "tags": {"values": ["x"]} }
```

This makes "missing" vs "explicit zero" impossible to confuse.

## Quick walkthrough

The samples use two schema versions:

* [`examples/schema_person_v1.json`](examples/schema_person_v1.json)
* [`examples/schema_person_v2.json`](examples/schema_person_v2.json) — adds
  optional `age` (7), packed repeated `scores` (8), `nickname` (10), and
  `Address.city` (3).

Self-contained requests (schema inlined) are generated by:

```bash
python3 examples/build_requests.py
```

### 1. Encode / decode

```bash
# encode a v1 message (id explicitly 0, email omitted -> missing)
bse -f examples/req_encode_v1.json > enc.json

# decode it back under v1
B64=$(jq -r .result.data_b64 enc.json)
jq -n --arg b64 "$B64" --slurpfile s examples/schema_person_v1.json \
  '{op:"decode",schema:$s[0],data_b64:$b64}' | bse --pretty
```

The output shows `"id":{"present":0}` and `"email":{"missing":true}`.

### 2. Read new data with an old schema (unknown fields)

```bash
B64V2=$(bse -f examples/req_encode_v2.json | jq -r .result.data_b64)
jq -n --arg b64 "$B64V2" --slurpfile s examples/schema_person_v1.json \
  '{op:"decode",schema:$s[0],data_b64:$b64}' | bse --pretty
```

`age`, `scores`, `nickname` (and nested `addr.city`) appear under
`__unknown__` with their raw wire bytes; known fields still decode.

### 3. Forward unknown fields through the old schema

```bash
jq -n --arg b64 "$B64V2" --slurpfile s examples/schema_person_v1.json \
  '{op:"forward",schema:$s[0],data_b64:$b64,"set":{"name":"Edited by v1"}}' \
  | bse > fwd.json
# Decode the forwarded bytes under v2 again: age/scores/nickname survive.
B64F=$(jq -r .result.data_b64 fwd.json)
jq -n --arg b64 "$B64F" --slurpfile s examples/schema_person_v2.json \
  '{op:"decode",schema:$s[0],data_b64:$b64}' | bse --pretty
```

### 4. Compatibility check

```bash
bse --pretty -f examples/req_compat_v1_v2.json          # compatible
```

A third schema changes `email` from `string` to `int32` and adds a `required`
field:

```bash
jq -n --slurpfile o examples/schema_person_v1.json \
      --slurpfile n examples/schema_person_v3_incompatible.json \
  '{op:"compat",old_schema:$o[0],new_schema:$n[0]}' | bse --pretty
```

Both changes are reported `incompatible`, and decoding old bytes under v3 is
rejected with a typed error.

### 5. Truncation

```bash
jq -n --arg b64 "$B64" '{op:"truncate",data_b64:$b64,"keep":20}' | bse
# feeding the resulting data_b64 back to "decode" returns
# {"ok":false,"error":"unexpected end of input"} (exit code 1), never a panic
```

A full, reproducible walkthrough is in
[`examples/demo.sh`](examples/demo.sh).

## Testing

```bash
cargo test              # unit + integration tests
cargo clippy --all-targets -- -D warnings

```

Test groups:

| File | Covers |
|------|--------|
| `src/wire.rs` tests | varint/zig-zag vectors, tag validation, EOF vs truncation, LEN overrun, envelope |
| `tests/evolution.rs` | bidirectional old/new reads, unknown-field forwarding, nested unknowns, incompatible type/cardinality rejection, truncation |
| `tests/limits.rs` | `max_value_len`, `max_output`, `max_depth`, encode size cap |
| `tests/streaming.rs` | one-byte-at-a-time stream decode; decoder never reads past the envelope payload |
| `tests/codec_extra.rs` | packed↔unpacked cross-reads, every scalar type, malformed bool/UTF-8, int width |
| `tests/api_e2e.rs` | the JSON `encode/decode/forward/compat/truncate` operations end to end |

## Acceptance criteria mapping

| Requirement | Where |
|-------------|-------|
| Field-numbered message format | `FORMAT.md` §3, `src/wire.rs` |
| Optional fields | `Cardinality` in `src/schema.rs`, presence wrappers in `src/jsonio.rs` |
| Unknown-field preservation/forwarding | `RawField` capture in `src/codec.rs`, `forward` op, `unknown_fields_are_forwarded_byte_for_byte` |
| Repeated-field strategy | unpacked (one tag/value) and packed scalar forms, cross-readable (`packed_writer_read_by_unpacked_reader_and_vice_versa`) |
| Incompatible type changes rejected | `reject_wire_mismatch` + `src/schema.rs` matrix; `incompatible_type_change_is_rejected` |
| New/old schema read each other's data | `old_data_reads_under_new_schema`, `new_data_reads_under_old_schema` |
| Unknown-field forwarding + truncation tests | `tests/evolution.rs`, `tests/api_e2e.rs` |
| Missing vs explicit zero | `explicit_zero_survives_and_differs_from_missing`, `explicit_false_and_empty_string_are_present`, `explicit_zero_wrapper_is_not_missing` |
| Memory/output limits | `Limits`, `tests/limits.rs` |
| Documented format | `FORMAT.md` |
| Core algorithms self-implemented | all of `src/` (no dependencies) |
| Source + README + request samples + automated tests | this repo |
| Actually run, results recorded | `RUNLOG.md` |

## Design notes / limitations

* Repeated `string`/`bytes`/message fields are always unpacked (packed is
  defined for numeric scalars only, matching the spec).
* Field numbers 1..=2²⁹−1; removed field numbers should never be reused.
* This is a library + CLI/JSON backend; there is intentionally no frontend.
