# metricrollup — 指标保留层压缩（Metrics Retention-Layer Rollup）

纯后端可观测性数据处理样例：HTTP 摄入与查询、本地 JSON 快照持久化、
合成数据驱动；把原始秒级样本**增量**降采样到分钟层和小时层，每个桶保存
`count / sum / min / max`，**绝不从平均值再平均**。支持迟到样本合并与历史
修订向上传播；原始数据被保留策略裁剪后，哪些细节不可恢复会被明确拒绝并
记录。

无前端、无外部监控平台依赖、无第三方 Go 依赖（仅标准库）。

## 为什么存 count/sum/min/max，而不是平均值

一个桶只存 `mean` 时，粗层无法精确聚合：两个分钟桶的均值不能直接平均，
因为它们的样本数可能不同。本系统每个桶保存：

| 字段 | 含义 | 粗层合并方式 |
|------|------|--------------|
| `count` | 桶内原始样本数 | 相加 |
| `sum` | 原始值之和 | 相加 |
| `min` | 最小值 | 取较小 |
| `max` | 最大值 | 取较大 |

`mean = sum / count` 仅在查询响应中派生展示，不落任何存储层。因此：

- 分钟桶 = 对该分钟内**原始样本**做 count/sum/min/max 归并；
- 小时桶 = 对该小时内 **60 个分钟桶的聚合结果**再归并（输入仍是
  count/sum/min/max，不是均值）；
- 合并且满足交换律/结合律，样本乱序、迟到到达结果完全一致。

## 增量降采样与迟到修订

**增量摄入（append）**：每条新样本直接 `Merge` 进所在分钟桶和小时桶，
`Merge` 交换且结合，所以先到、后到、跨边界迟到结果相同，不需要重放整桶。

**历史修订（correct）**：某一秒的值被改写时，因为无法从已合并的
sum/min/max 中"减"掉旧值，采用自底向上重算：

1. 用该秒的新值替换 raw 层该秒的全部值；
2. 所属**分钟桶**从保留的 raw 秒数据重算；
3. 所属**小时桶**从其 60 个分钟桶重算。

跨分钟/小时边界的修订（`:00`、`:59`、`:59:59`）由对齐函数保证只影响
正确的桶。

## 明确不可恢复的细节（重要语义）

以下信息一旦从 raw 层消失（保留裁剪）或从未采集，就**无法**从分钟/小时层
恢复，系统对这类修订返回 `409 Conflict`
（`no raw samples retained at that timestamp ...`）：

1. **桶内精确值与时间戳分布**：分钟层只留 count/sum/min/max，不知道第 2
   个样本是什么值、落在哪一秒。
2. **min/max 不可"反合并"**：若被修订的恰好是贡献 min 或 max 的样本，
   没有原始值就无法算出新的 min/max（sum 尚可线性修正，min/max 不行）。
3. **均值不可补救**：只存均值的系统连权重都丢失；本系统保留了 count/sum，
   但仍不足以还原个体值。
4. **同一秒多个点被合并**：粗层无法区分"1 个值为 10 的点"与"2 个值之和
   为 10 的点"。
5. **修订窗口外的写入**：raw 被裁剪后，写入只能作为新样本追加，不能声称
   是对历史值的精确替换。

这是有意的设计：宁可明确拒绝并暴露信息损失，也不给出看似精确实则错误的
聚合值。分钟/小时层在裁剪后**仍可查询**（有损但已落库的聚合不丢）。

## 项目结构

```
cmd/server/main.go        HTTP 服务入口（快照加载、优雅退出）
cmd/verify/main.go        验收程序：多密度/跨边界/空桶/修订/裁剪 场景 vs 原始重算
internal/model/           Sample、Series、确定性序列键
internal/rollup/          桶对齐与 Agg(count/sum/min/max) 合并数学
internal/store/           三层存储、增量降采样、修订传播、保留裁剪、JSON 快照
internal/server/          HTTP 路由、参数校验、错误码
internal/synthetic/       确定性合成数据（周期/抖动/空洞）
internal/verify/          独立"原始重算"参考预言机与逐桶比对
examples/                 请求 JSON 与端到端 curl 脚本
```

## HTTP API

| 方法 路径 | 说明 |
|-----------|------|
| `GET /healthz` | 健康检查 |
| `POST /v1/ingest` | 批量摄入样本，增量合并到分钟/小时层 |
| `POST /v1/correct` | 改写某一秒的值并向上传播修订 |
| `GET /v1/query` | 按 `raw/minute/hour` 层查 `[start,end)`，空桶以 `count=0` 显式返回 |
| `GET /v1/series` | 列出全部序列 |
| `POST /v1/admin/prune` | 裁剪早于 cutoff 的 raw 样本（分钟/小时不动） |
| `POST /v1/admin/snapshot` | 原子写入 JSON 快照 |

摄入请求体：

```json
{"samples":[{"metric":"cpu.usage","labels":{"host":"h1"},"ts":7200,"value":12.5}]}
```

查询参数：`metric`、`layer=raw|minute|hour`、`start`/`end`（Unix 秒或
RFC3339）、可重复的 `label=k=v`。

状态码：`400` 参数/JSON 非法；`404` 序列不存在；`409` 修订不可恢复
（该秒无保留的 raw 数据，从未采集或已裁剪）。

## 构建、运行、测试

需要 Go 1.22+（本项目仅用标准库）。

```bash
go build ./...                 # 编译
go test -race -cover ./...     # 全部测试（竞态检测 + 覆盖率）
go run ./cmd/verify            # 验收程序（全过则退出码 0）
go run ./cmd/server -addr :8080 -data ./data/snapshot.json
./examples/requests.sh         # 对运行中的服务执行端到端 curl
```

## 验收方法与结果（本次实跑）

验收预言机 `internal/verify` **只遍历原始样本**独立重算每个桶，再与服务端
三层查询结果逐桶比较 count/sum/min/max（容差 1e-9 相对误差）。均值不参与
比对（它是派生字段）。

`go run ./cmd/verify` 覆盖：

- **不同样本密度**：1s/5s 密集、37s/90s 稀疏（带抖动，制造跨边界落点）；
- **空洞**：周期性跳点产生空分钟、空小时；
- **乱序迟到**：确定性洗牌 + 首批样本延迟到队尾；
- **跨层边界**：修订点覆盖某分钟 `:00`/`:59`、某小时首秒与末秒
  `02:59:59`/`03:00:00`、桶中间；
- **历史修订传播**：改写后用"修订后的原始事实"重算预言机，校验三层一致；
- **空桶**：空桶 `count=0` 且数值字段为 `null`，不被静默跳过；
- **裁剪后修订被拒**：raw 裁剪返回不可恢复错误，粗层仍可查且与原预言机一致。

实跑结果：**10/10 场景通过**。单元/HTTP 测试全部通过（`-race`），
internal 包语句覆盖率合计 **91.9%**（model/rollup/synthetic 100%，
store 88.7%，verify 89.5%，server 92.6%）。详细命令、原始输出与开发中
出现过并修复的失败项见 [docs/RUNLOG.md](docs/RUNLOG.md)。

## 持久化与局限

- 持久化是**全量 JSON 快照**（写临时文件 + rename 原子替换 + fsync），
  不是 WAL：上次快照之后、崩溃之前确认的摄入会丢失。
- 全内存、单实例、无鉴权与限流，定位为本地可运行的教学/样例，不做生产
  级扩展（分片、下采样任务调度、TTL 自动裁剪等未实现）。
- 时间戳按 UTC Unix 秒处理；同一秒同序列多点会在 raw 层保留为数组，
  `correct` 会整体替换该秒。
