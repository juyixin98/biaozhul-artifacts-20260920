# amptrain — mixed-precision trainer for small synthetic networks

A from-scratch, NumPy + FastAPI implementation of **mixed-precision training**
for a small MLP, built around one hard constraint:

> **Master weights, low-precision forward parameters, and optimizer state are
> three physically separate tensor families.**

All data is **local and synthetic** — there are no external accounts, network
participants, or real business data. Overflow is induced deterministically
either by an *amplification* factor on the synthetic inputs or by an
over-large *loss scale*.

---

## 1. What is implemented

### The core separation (tensor-type layer — `amptrain/tensors.py`)

| Family | dtype | role | mutated by optimizer? |
|---|---|---|---|
| `MasterWeights` | **fp32** | the authoritative parameters | yes (only these) |
| `LowPrecisionParams` | **fp16** (or fp32 control) | throwaway cast used for every forward/backward | never |
| `OptimizerState` | **fp32** | independent momentum buffers, not views | yes |
| `GradientAccumulator` | **fp32** | window accumulator for *unscaled* gradients | per-window |

Each micro-batch does a **fresh fp32→fp16 cast**; the cast is a copy, so no
low-precision value is ever written back into the master weights.

### Compute graph (`amptrain/graph.py`)

A 2-layer MLP `Y = act(X @ W1) @ W2` with MSE. All trainable matmuls, the
**scaled** loss, and the upstream gradient are computed in the low-precision
dtype. Three stages are checked for finiteness **explicitly and separately**:

1. `forward_output`
2. `scaled_loss`
3. `backward_grad`

An fp32/`loss_fp32` value is computed independently for logging only.

### Training state (`amptrain/trainer.py`, `scaler.py`, `scheduler.py`)

* **Window semantics** — one optimizer step commits exactly
  `accumulation.micro_batches` micro-batches.
* **Overflow ⇒ skip the whole window, no partial commit.** Partial
  accumulator is discarded; master weights and momentum are **bit-identical**
  before/after; the LR schedule does **not** advance.
* **Dynamic loss scaling** — on skip: `scale *= backoff_factor` (clamped at
  `min_scale`, never reaches 0) and the good-step streak resets. After
  `growth_interval` consecutive *committed* steps: `scale *= growth_factor`
  (capped at the fp16 max).
* **Step counters are explicit and distinct** — `window_index` (attempted),
  `committed_steps` (updates applied), `skipped_windows`. Only committed
  steps advance the LR schedule (`constant` or `step`).
* **Checkpoints** (`amptrain/checkpoint.py`) persist master weights,
  momentum, counters, **scaler state (scale + growth tracker)**, LR progress,
  config and RNG state; loading validates format, shapes, dtypes and a
  finite/positive scale.

### Validation (`amptrain/reference.py`)

An **independent fp64 oracle** re-implements the network and SGD-momentum
dynamics without importing the trainer's math. Tests compare committed
trajectories against it, assert bit-exact master-weight conservation on
skips, and derive schedule expectations from first principles. **Reference
answers are not generated by the code under test.**

### Service (`amptrain/api.py`, `schemas.py`, `service.py`)

A FastAPI app creates runs, drives windows (auto synthetic fixture or custom
finite batches), inspects the event log, and saves/loads checkpoints.

## 2. Error semantics (important)

Overflow during training is a **domain status, not an exception and never a
silent success**:

* A window that overflows returns `status: "skipped"` with the
  **stage** (`forward_output` / `scaled_loss` / `backward_grad`), the
  **micro-batch index**, the names of the **non-finite tensors**, and the
  scale **before/after**.
* It is logged as `window_skipped` with
  `decision: "drop_window_no_partial_commit_backoff_scale"`.
* Exceptions are reserved for **contract violations**, each with a stable
  machine-readable code:

  | code | when |
  |---|---|
  | `CONFIG_INVALID` | bad hyperparameters / dtype / dim mismatch |
  | `INPUT_INVALID` | wrong shape/dtype, wrong micro-batch count, or inf/NaN passed in |
  | `RUN_NOT_FOUND` / `CHECKPOINT_NOT_FOUND` | unknown id / missing path |
  | `CHECKPOINT_CORRUPT` | bad format, shape/dtype mismatch, non-positive saved scale |
  | `NONFINITE_UNEXPECTED` | a non-finite value where the checked path forbids one (a bug) |
  | `INTERNAL_ERROR` | any unexpected exception (never remapped to success) |

* HTTP failures always use
  `{"success": false, "error": {"code", "message", "detail"}}` with a 4xx/5xx
  status. Overflow inputs themselves must be **finite** — passing literal
  inf/NaN is rejected with `INPUT_INVALID`, because the point is to detect
  overflow from genuine fp16 range limits, not from poisoned input.

```
src/amptrain/
  config.py       validated immutable configuration
  errors.py       error taxonomy
  tensors.py      master / low-precision / optimizer-state separation
  graph.py        low-precision forward/backward + staged finite checks
  scaler.py       dynamic loss-scaling state machine
  scheduler.py    LR schedule (committed-step driven)
  optimizer.py    fp32 SGD+momentum on master weights
  data.py         local synthetic fixtures (with amplification knob)
  trainer.py      window/skip/commit semantics, counters
  checkpoint.py   save/load (incl. scaler state) with integrity checks
  reference.py    independent fp64 oracle
  events.py       run-correlated structured event log (versions + basis)
  api.py          FastAPI app
  schemas.py      pydantic HTTP schemas
  service.py      in-memory run registry
tests/            independent pytest suite (82 tests)
scripts/demo.py   local end-to-end demonstration
```

## 5. Reproduce the results

### Run the tests (they really run and report)

```bash
python3 -m pytest tests/ -v
# with coverage (>=80% gate configured in pyproject.toml):
python3 -m pytest --cov=amptrain --cov-report=term-missing
```

The suite covers, with concrete assertions (not "interface is callable"):

* the three tensor families have distinct dtypes and non-shared memory;
* **amplified finite input triggers an overflow**, located at a named stage;
* a skipped window **backs the scale off (128→64)** and leaves master weights
  **bit-identical**;
* **any** overflow in a 3-micro-batch window drops the entire window (the two
  good micro-batches are not partially committed);
* skipped windows do not advance the LR schedule, and after checkpoint
  restore the resumed step uses the correct LR;
* the **fp32 control run** on the same healthy data with an over-large scale
  commits uninterrupted and converges, while fp16 skips, backs the scale off
  monotonically, then recovers;
* committed trajectories match the **fp64 oracle** within fp16 forward error,
  and training genuinely reduces the loss.

### Run the local demo

```bash
python3 scripts/demo.py                 # add --log-dir logs for JSONL output
```

It prints, per `run_id`, each window's verdict with the basis for the
decision, verifies master-weight conservation across the skip, shows the
fp32 vs fp16 contrast, accumulation atomicity, and checkpoint/restore.

### Run the service

```bash
python3 -m amptrain                     # or: uvicorn amptrain.api:app --port 8000
```

Then in another shell:

```bash
# health / versions
curl -s localhost:8000/healthz

# create a healthy fp16 run, run 3 windows
RID=$(curl -s -X POST localhost:8000/runs -H 'content-type: application/json' \
  -d '{"n_samples":64}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["run"]["run_id"])')
curl -s -X POST localhost:8000/runs/$RID/windows/auto -d '{"n_windows":3}' \
  -H 'content-type: application/json'

# create a run whose synthetic inputs are amplified enough to overflow fp16
BAD=$(curl -s -X POST localhost:8000/runs -H 'content-type: application/json' \
  -d '{"amplification":1000}' | python3 -c 'import sys,json;print(json.load(sys.stdin)["run"]["run_id"])')
curl -s -X POST localhost:8000/runs/$BAD/windows/auto -d '{"n_windows":1}' \
  -H 'content-type: application/json'
# -> outcome.status == "skipped", overflow_stage == "scaled_loss",
#    scale 128 -> 64

# run-correlated event log with versions and verdict basis
curl -s localhost:8000/runs/$BAD/events
```

## 6. Why the two overflow tests look different

There are two honest ways to make the low-precision range the deciding
factor, and the project tests both:

1. **Amplified finite inputs** (`amplification=1000`). fp16's *scaled* loss
   overflows while the identical values stay finite in fp32, so fp16 skips
   and fp32 commits. Note the *true* unscaled gradient is genuinely large
   there, so a raw fp32 update would diverge — which is exactly the damage
   the skip prevents; this test asserts the **per-window decision contrast**
   and fp16 **recovery**, not that adversarial input trains well in fp32.
2. **Healthy inputs with an over-large loss scale** (`init_scale=32768`).
   The real gradients are small and healthy (fp32 converges
   ~3.96 → ~1.06); fp16 skips purely because the *scaled* values leave
   range, then dynamic backoff (32768→8192) restores committing and fp16
   still converges overall. This is the textbook dynamic-loss-scaling loop.

## 7. Design notes

* All core value objects are immutable dataclasses; updates return new
  instances, so partial state can never be mutated in place and then
  half-committed.
* Stats (grad/weight norms) are accumulated in fp64 so logging itself never
  overflows.
* NumPy scalar overflow/NaN warnings are silenced only inside the explicitly
  checked low-precision compute path, where they are expected and classified.
* `float32` is offered as a low-precision dtype deliberately — it is the
  full-precision control. `bfloat16` is not advertised because the target
  NumPy build does not expose it.
